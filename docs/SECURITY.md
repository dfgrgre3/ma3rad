# سياسة الأمان — CeramiSys ERP

يوضّح هذا المستند نموذج التهديد والضوابط الأمنية المطبّقة في التطبيق، وكيف
تُدار الأسرار والصلاحيات والاتصالات الخارجية. أي تغيير في هذه الضوابط يحتاج
اختباراً في `test/electron-security.test.ts` أو الاختبار المرتبط بالخدمة.

---

## 1. نموذج التهديد

التطبيق مكتبي يعمل على جهاز المستخدم، ويعالج بيانات مالية وشخصية حساسة.
الافتراضات:

- جهاز المستخدم قد يكون مشتركاً بين عدة موظفين أو عرضة لوصول فيزيائي.
- الشبكة المحلية/الإنترنت غير موثوقة.
- محتوى الواجهة (نصوص، أسماء عملاء، ملفات مستوردة) غير موثوق ويجب عدم تفسيره
  كـ HTML أو كود.
- المنصة المركزية طرف موثوق للترخيص والتكوين، لكن انقطاعها لا يجب أن يوقف
  العمل المحلي أكثر من سماحية عدم الاتصال.

خارج النطاق: حماية الجهاز من مستخدم يملك صلاحيات مدير النظام، أو من برمجيات
تسجيل الشاشة/لوحة المفاتيح.

## 2. أمن عملية Electron

| الضابط | التنفيذ |
| --- | --- |
| عزل السياق | `contextIsolation: true` + `sandbox: true` |
| منع Node في الواجهة | `nodeIntegration: false` |
| جسر وحيد | `electron/preload.js` يعرّض واجهات محددة فقط |
| التحقق من مصدر IPC | `validateIpcSender` عبر `electron/security.js`؛ يرفض أي إطار غير رئيسي أو عنوان غير مطابق |
| منع الملاحة | `will-navigate` يمنع الخروج من عنوان التطبيق |
| الروابط الخارجية | تُفتح في المتصفح النظامي فقط |
| حدود الحجم | قاعدة البيانات ≤ 500MB، بيانات الطباعة ≤ 10MB |
| نسخة واحدة | `requestSingleInstanceLock` |
| إغلاق آمن | `gracefulShutdown` يضمن حفظ القاعدة قبل الخروج |

التحقق من العنوان يقارن مسار الملف الفعلي (بعد فك الترميز والتطبيع) وليس نص
URL، لتغطية اختلافات Windows في حالة الأحرف والتهريب.

### توقيع Windows والتحديثات

- كل إعدادات بناء Windows تفرض توقيع Authenticode؛ يفشل البناء إذا تعذر
  التوقيع (`forceCodeSigning`).
- مشغّل البناء يشترط `CERAMISYS_PUBLISHER_NAME`، ويُضمّن اسم الناشر في بيانات
  التحديث كي يرفض `electron-updater` أي مُثبّت تحديث بتوقيع ناشر مختلف.
- زوّد بيئة البناء بشهادة موثوقة عبر `CSC_LINK` و`CSC_KEY_PASSWORD` (أو مخزن
  شهادات معتمد على عامل البناء)، واضبط `CERAMISYS_PUBLISHER_NAME` على اسم
  الناشر المطابق للشهادة. خزّن بيانات الشهادة وكلمة مرورها كأسرار في CI؛
  لا تحفظها في ملفات المشروع أو المستودع.
- لا تنشر تحديثات إلا من نسخة موقّعة بالشهادة نفسها. إعداد macOS يحتاج
  شهادة Apple وإعداد التوثيق notarization الخاص به بصورة منفصلة.

## 3. أمن الواجهة (XSS وCSP)

- سياسة CSP تُحقن وقت البناء من `vite.config.ts`:
  - `default-src 'self'`
  - `script-src 'self' 'wasm-unsafe-eval'` (لازم لـ sql.js، بدون `unsafe-inline`)
  - `object-src 'none'` و`base-uri 'none'`
  - `connect-src` يسمح بـ HTTPS وloopback فقط
- أي عرض لبيانات مستخدم داخل HTML يجب أن يهرّب النص (مثال: `esc()` في
  `PosView`). لا تستخدم `dangerouslySetInnerHTML` مع بيانات غير موثوقة.
- أسماء العملاء/المنتجات القادمة من الاستيراد تُعامل كنص دائماً.

## 4. الأسرار والتشفير

| البيان | الحماية |
| --- | --- |
| مفتاح قاعدة البيانات | مفتاح AES-256-GCM عشوائي، يُشفَّر بـ `safeStorage` ويُخزَّن في مجلد التطبيق |
| النسخ الاحتياطية | مشفّرة بـ AES-256-GCM مع IV فريد لكل نسخة |
| بيانات الدخول المحفوظة | ملف `remembered-login.enc` مشفّر عبر `safeStorage` |
| رمز الجهاز المركزي | يُخزَّن محلياً ولا يُرسل إلا عبر HTTPS |
| كلمات المرور | تجزئة `bcrypt` (وليس تشفيراً قابلاً للعكس) |

`safeStorage` يعتمد على مخزن مفاتيح النظام؛ عند عدم توفره يفشل التطبيق بأمان
بدل تخزين أسرار بنص صريح.

## 5. الاتصال بالمنصة المركزية

- `CentralLicenseService.getSecureServerUrl()` يرفض أي عنوان غير `https://`،
  ويسمح بـ `http://localhost` فقط للتطوير.
- `setServerUrl` يتحقق قبل الحفظ ويعيد القيمة السابقة عند الرفض.
- رمز الجهاز (`credential`) يُرسل في ترويسة `Authorization` وليس في رابط URL،
  حتى لا يظهر في السجلات أو تاريخ الملاحة.
- التحقق من الترخيص: عند الإقلاع وكل 6 ساعات، مع سماحية 14 يوماً دون اتصال.
  بعد انتهائها يتوقف التطبيق (fail closed) حتى يُتحقق مجدداً.
- التكوين المركزي يُطبَّق ذرّياً مع تدقيق؛ ولا يُطبَّق `businessType` إلا إذا
  كان ضمن `BUSINESS_TYPES` المعروفة.

## 6. الصلاحيات والحدود

### الصلاحيات

- `PermissionService.can` = صلاحية الدور + قيود الصفحة/الوحدة المركزية → للواجهة.
- `PermissionService.hasRoleGrant` = صلاحية الدور فقط → للخدمات الخلفية.
- `PermissionService.require` يرمي خطأً واضحاً عند الرفض.

الفصل مقصود: قيود إخفاء الصفحات مركزياً يجب ألا تمنع عمليات خلفية مشروعة
(مثل ترحيل قيد محاسبي من عملية مسموحة).

### حدود الاستخدام

`CentralUsageLimitService.assertWithin` تُستدعى داخل الخدمات وليس في الواجهة:

| الحد | موضع الفرض |
| --- | --- |
| `maxUsers` | `AuthService.createUser` |
| `maxBranches` | `BranchService.createBranch` / `OperationsService.createBranch` |
| `maxWarehouses` | `OperationsService.createWarehouse` |
| `maxEmployees` | `EmployeeService.create` |
| `maxInvoices` | `sales/invoiceCreation.createSalesInvoice` |

بهذا لا يمكن تجاوز الحدود عبر استدعاء الخدمة مباشرة أو عبر مسار بديل.

## 7. التدقيق

- `AuditLoggerService` يسجّل أحداث الدخول والخروج ومحاولات الفشل وتغيير كلمات
  المرور والصلاحيات.
- العمليات الحساسة على المنصة المركزية (تطبيق إعدادات، إضافة/تحديث منشأة
  وفروع، مستخدمون) تُسجَّل في سجل التدقيق مع الفاعل والوقت.
- يُفضّل مراجعة السجل دورياً من شاشة الإدارة.

## 8. التبعيات

- `npm audit --omit=dev` يجب أن يبقى **0 ثغرات**.
- تمت ترقية `react-router-dom` إلى `7.18.5` لمعالجة:
  - CVE إعادة التوجيه المفتوح عبر الشرطة العكسية في `<Link>` و`useNavigate`.
  - حقن المُنشئ عبر `deserializeErrors()` في SSR (غير قابل للاستغلال هنا لأن
    التطبيق SPA بـ `HashRouter` بلا SSR، لكن الترقية تغلق الثغرة نهائياً).
- حُذفت `jspdf` و`jspdf-autotable` غير المستخدمتين (كانتا مصدر ثغرات حرجة).
- أضف أي حزمة جديدة بعد مراجعة سمعتها وحجمها وسكربتات التثبيت الخاصة بها.

## 9. الإبلاغ عن ثغرة

لا تفتح بلاغاً عاماً يحتوي تفاصيل قابلة للاستغلال. أرسل إلى مالك المشروع:
الوصف، خطوات الاستعادة، الإصدار، والأثر المتوقع. سيُرد خلال 72 ساعة عمل،
ويُنسّق موعد الكشف بعد إصلاح الإصدار المتأثر.

# نظام سوبر أدمن v2 — حسابات الإدارة، الأدوار والصلاحيات (مصفوفة كاملة)

> **الحالة:** مُنفذ بالكامل داخل التطبيق الحالي (`/platform/*`). لا يوجد تطبيق مستقل بعد — الفصل في `central-admin` يبقى خياراً مستقراً للمرحلة التالية.

هذا المستند يصف ما نُفذ من توصيات القسم 6، وكيف تُدار كل ميزة تشغيلياً.

---

## 1) نظرة عامة — ثلاث طبقات فرض لا تُكتفى بإخفاء الأزرار

| الطبقة | أين | كيف |
|---|---|---|
| **Frontend** | `AppRouter.tsx`, `PlatformLayout.tsx`, الصفحات | `PlatformRouteGuard` + `canAccessPermission()`/`canPlatformPermission()` تخفي الصفحة والأزرار والعمليات. |
| **Backend/API (طبقة الخدمة)** | `PlatformAdminService` + `PlatformAuthorizationService` | كل دالة خدمة تُلزم الصلاحية عبر `requirePlatformAccess(module, 'platform.<module>.<action>')`. 176 موضع تحقق أصبحت بالأكواد الدقيقة (وليس الوحدات). طلب API يدوي يُرفض (مرفوض افتراضياً إن لم تملك الكود). |
| **Data Scope** | `platform_staff.data_scope` + `platform_staff_scopes` | الموظف برؤية/تعديل «عملاء محددين» فقط: `listTenants` ترشّح النتائج، و`getTenant`/`getTenantProfile`/كل دوال التعديل ترفض العميل خارج النطاق برسالة `(نطاق البيانات)`. |

> **إخفاء زر الحذف لا يمنع تنفيذ الحذف بطلب API مباشر** — لذلك كل عملية حذف (نظريات) ممنوعة أيضاً في طبقة الخدمة، وبعض الأدوار لا تملك الكود أصلاً.

## 2) نموذج الصلاحيات — من قائمة صغيرة إلى مصفوفة كاملة

### 2.1 الكتالوج (`platformPermissionCatalog.ts`)
- **28 قسمًا** (أقسام الأعمال: العملاء، الموظفون، الاشتراكات، الفواتير، التراخيص، الأجهزة، الخطط، المنتج، الإصدارات، الدعم، الإعدادات، الأمان، النسخ الاحتياطي، سجل العمليات، التحليلات، المزامنة، التكاملات، الإشعارات، السياسات، العمليات، النظرة العامة، إعدادات النشاط/الهوية/التخصيص/التكوين، صحة النظام/المنصة، مركز التحكم، الطوارئ، بوابة العملاء، مالك المنصة).
- **6 أفعال قياسية لكل قسم (عند انطباقها):** عرض `view`، إنشاء `create`، تعديل `update`، حذف `delete`، اعتماد `approve`، تصدير `export`. مثلًا: «الإعدادات» بدون إنشاء/حذف، و«النسخ الاحتياطي» بدون تعديل/حذف — بالضبط كما هو مطلوب.
- **عمليات خاصة (`special`)** مستقلة تمامًا: `platform.tenants.suspend/activate/manage_users`، `platform.staff.deactivate/reset_password/assign_role/manage_permissions/revoke_sessions`...
- كل صلاحية = رمز `platform.<module>.<action>` مستقل. لا توجد صلاحية «افتح الصفحة» فقط.

### 2.2 التخزين والبذر (migration `200_platform_rbac_v2`)
- `platform_permissions` (الكتالوج) + `platform_role_permissions` (role_code × permission_code) — تُزرع مصفوفات الأدوار الستة بالقدرات المُتفق عليها حاليًا (لا فقدان صلاحية عند الترقية). البذر idempotent ولا يطمس أي تعديل لاحق على المصفوفة.
- `platform_staff` اكتسب: `must_change_password`، `deleted_at` (حذف منطقي)، `data_scope` (`ALL|LIMITED`)، `invited_by`.
- `platform_staff_invites` (رموز دعوة محدودة المدة، تخزين sha-256 فقط)، `platform_trusted_devices`، `platform_staff_scopes`.
- `platform_settings.platform_mfa_enforcement` = `off|optional|required`.
- migration `201_platform_staff_2fa`: جدول `platform_staff_2fa` (نفس مخطط `user_2fa` لكن بدون FK — موظفو المنصة ليسوا صفوفًا في `users`).

### 2.3 التحقق (`PlatformAuthorizationService`)
- `canAccessPermission(role, code, override)` — **المنع الافتراضي**: الرمز غير الممنوح صراحةً يُرفض. `SUPER_ADMIN` يملك `*` دائمًا.
- المصفوفة مخزّنة في قاعدة البيانات مع كاش + `invalidatePlatformRolePermissionsCache()` عند كل كتابة.
- التوافق مع القديم: `canAccessModule` ما زالت تعمل (تستدعى في 200+ موضعًا) وأصبحت تمنح عند امتلاك أي صلاحية `platform.<module>.*` صراحةً، وتمرر الرموز المنقّطة كما هي.

### 2.4 الواجهة
- **`/platform/staff`** — مركز التحكم في حسابات الإدارة (انظر §3).
- **`/platform/roles`** — مصفوفة كاملة (جديدة): مصفوفة أساسية (القسم × 6 أفعال) + مصفوفة «العمليات الخاصة» (كل عملية على حدة). حفظ فوري لكل دور، تمييز الأدوار المعدّلة، `SUPER_ADMIN` مقفل دائمًا بكل الصلاحيات.
- التنقل الجانبي والحُرّاس يستخدمان `PLATFORM_ROUTE_PERMISSION_MAP` (رمز صلاحية لكل مسار).
- `canPlatformPermission('platform.tenants.delete')` للأزرار.

## 3) مركز التحكم في حسابات الإدارة (`/platform/staff`)

| الوظيفة | الحالة |
|---|---|
| إنشاء موظف (الاسم، البريد، الهاتف، الدور، كلمة مرور أولية) | ✅ مع فرض تغيير كلمة المرور عند أول دخول |
| دعوة موظف (رابط محدود المدة + بريد إلكتروني) | ✅ `platform_staff_invites` — رمز 256 بت (يُعرض مرة واحدة)، الرابط `/#/accept-staff-invite/<token>`، التفعيل أحادي الاستخدام، إبطال الدعوة قبل الاستخدام، دور الموظف يُحدد من الدعوة، البريد هو هوية الحساب |
| تسجيل دخول مستقل عن حسابات عملاء ERP | ✅ عبر `platform_staff` + جلسة `psess_*` (12h) |
| تعديل البيانات | ✅ الاسم، البريد، الهاتف، الدور، التفعيل |
| تفعيل وتعطيل | ✅ التجميد **ينهِي الجلسات المفتوحة فورًا** |
| إعادة تعيين كلمة المرور | ✅ من المدير (تُفرض مصادقة التغيير + تُنهي الجلسات + سجل `SECURITY`) — لا يمكن لموظف آخر إعادة تعيين كلمة مرور `SUPER_ADMIN` |
| فرض تغيير كلمة المرور | ✅ يدويًا بالزر لكل موظف، أو قسريًا بعد إعادة التعيين، أو بتعديل كلمة المرور من مدير |
| MFA مصادقة متعددة العوامل | ✅ TOTP (Google Authenticator…) + رموز استرداد ذات استخدام واحد + **إلزام مؤسسي اختياري** `off|optional|required` + امتثال لحظي لكل الموظفين + إعادة تعيين طارئة من مالك المنصة |
| إدارة الجلسات | ✅ قائمة كل الجلسات مع الجهاز والـ IP وآخر نشاط + إنهاء جلسة / كل الجلسات الأخرى |
| الأجهزة الموثوقة | ✅ «وثّق هذا الجهاز» (بصمة User-Agent/المنصة)، تمييزها في الجلسات، إلغاء توثيقها |
| سجل دخول الموظف | ✅ ناجح/فاشل/محظور مع السبب، قابل للتصفية (الفاشلة فقط) |
| حذف الموظف | ✅ **حذف منطقي** (`deleted_at`) — يمنع الدخول ويُنهي الجلسات ويبقي سجل التدقيق والإجراءات التاريخية |
| نقل الصلاحيات | ✅ نسخ الدور + التجاوزات + نطاق البيانات إلى موظف آخر مع `SECURITY` audit (من نفذ، بملاحظة، ومتى) وإنهاء جلسات الهدف |
| سجل الدخول + تدقيق | ✅ كل عملية في `platform_audit_logs` (سلسلة تجزئة ضد العبث — تم إصلاح خلل قراءتها (camelCase) في هذه الجولة) |

**من يرى/يغيّر؟** المصفوفة الافتراضية: `SUPER_ADMIN` كل شيء؛ `PLATFORM_ADMIN` كل شيء عدا حذف الموظفين ودوري مالك المنصة؛ الدعم/العمليات/الفوترة/التراخيص وفق نطاق صلاحياتهم في `PLATFORM_ROLE_DEFAULT_PERMISSIONS`.

## 4) الأمان التشغيلي والثغرات المسدودة في هذه الجولة

1. **`CentralAuditService` كان يرمي كل سجلات المراجعة بحقول `entityType:"undefined"`** — لأن `DatabaseManager.query()` يعيد المفاتيح camelCase وهنا يُقرأ `row.entity_type`. أُصلح (المدخل الآن camel افتراضي مع snake fallback) خصوصًا في خريطة `query()` ومع `record_hash` (سلسلة الـ tamper-proof لم تكن تربط أبدًا — كل سجل كان `GENESIS_...`).
2. **الدخول كان معطّلًا كليًا لموظفي `platform_staff`** (يقرأ `is_active` بينما المفتاح `isActive`) — أُصلح بالكامل + بُرمج عليه اختبار.
3. **تجميد الموظف لم يُنهِ جلساته** (في بعض المسارات) — الآن كل تجميد/حذف/إعادة تعيين/تغيير دور يوقظ الجلسات فورًا.
4. **الجلسات كانت تُحسب في مركز الأمان كأجهزة موثوقة دائمًا (مضلل)** — الآن العدّاد من `platform_trusted_devices` الفعلي.
5. **الامتثال لـ 2FA كان 0/N مزيفًا** — أصبح يعدّ الفعلي من `platform_staff_2fa`.
6. **ملفات صفحات المنصة لا تُصرّف** (JSX مكسور في `PlatformTenantsPage`, `PlatformBrandingSettingsPage`, `PlatformSecurityCenterPage`) — أُصلحت بدون تغيير السلوك المطلوب، وأكملتُ عنصر `canManage*` غير المعرف في 4 صفحات.

## 5) التشغيل — سيناريوهات جاهزة

### 5.1 إلزام المصادقة الثنائية على الجميع
`/platform/security-center` ← قسم «سياسة المصادقة الثنائية» ← **اجعلها إلزامية** (أو من `/platform/staff` ← تبويب «المصادقة والأمان»). الموظفون غير المفعّلين لا تُكسر جلساتهم الحالية، لكن لن يستطيعوا استخدام أي شاشة محمية حتى يفعّلوا 2FA من حسابهم (الزر موجود في نفس التبويب مع مسح QR).

### 5.2 إخراج موظف منتهي الخدمة (offboarding)
1. `/platform/staff` ← تجميد (يُنهي جلساته فورًا). 2. حذف منطقي. 3. انقل مسؤولياته بمعاهدة **نقل الصلاحيات** (من، إلى، ملاحظة) قبل أو بعد الحذف. 4. سجّل السبب في الملاحظة — تُختم في سجل التدقيق.

### 5.3 تدويل صلاحيات دور (مثلًا «الفوترة» تحتاج الاعتماد)
`/platform/roles` ← خانة `platform.billing.approve` لدور `BILLING_SPECIALIST` ← **حفظ التغييرات**. فورية على كل طلبات API وجميع الموظفين بذلك الدور.

### 5.4 إعادة تعيين MFA لموظف فقد هاتفه
`/platform/staff` ← تبويب «المصادقة والأمان» ← «إعادة تعيين MFA» (يظهر فقط لمن يملك `platform.staff.reset_password`) — لن يستطيع أحد إعادة تعيين MFA لـ `SUPER_ADMIN`.

### 5.5 نطاق بيانات لمندوب دعم (يرى عملاء معتمدين فقط)
`/platform/staff` ← أيقونة «نطاق البيانات» بجانب الموظف ← «عملاء محددون» ← ضع علامة على العملاء ← حفظ. لا يرى أي قائمة أو بحث عميل خارج النطاق، وأي طلب تعديل يُرفض في طبقة الخدمة.

### 5.6 استدعاء طارئ للكل
تجميد كل الموظفين (أو إنهاء الجلسات من `/platform/security-center` ← «إنهاء جميع الجلسات الأخرى») + مراجعة `/platform/audit`.

## 7) قرارات تصميمية / معروفة

- **الدعوة بالرابط لا ترسل بريدًا**: لا يوجد نقل SMTP في الكود حاليًا (تُخزّن إعداداته فقط في `/platform/settings`)؛ الرابط يُنسخ يدويًا ويُسلّم عبر قناة خارجية. نقطة الربط جاهزة عند توفر خدمة بريد.
- **البصمة للجهاز** = سلوك User-Agent/المنصة/اللغات/التوازي — ليست اعتمادية، ولا تُستخدم إلا لتمييز «جهاز موثوق» في الجلسات.
- **مصفوفة SUPER_ADMIN دائماً `*`** ولا يمكن تعديلها من أي دور آخر — حماية ضد إقفال المنصة.
- **DELETE فعلي ممنوع**: كل «حذف» موظف = منطقي (`deleted_at`).
- قراءة `row.xxx` في الكود القديم كانت تعتمد مفاتيح snake_case والمخزن يُرجع camelCase — أُصلح لكل مسارات الطاقم/الأمان بالتدريج؛ باقي المسارات القديمة التي ما زالت `row.xxx_yy` (إن وجدت) تعمل بالـ fallback آمن في الـ mappers.
- جلسة الموظف لا تتجاوز تجديدها صالحًا لأكثر من 12 ساعة، وإعادة التفعيل تتطلب كلمة المرور.
